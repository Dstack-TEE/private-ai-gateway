# E2EE v2 test vectors

These vectors pin the RFC 8785 JCS associated-data bytes used by the
[E2EE v2 compatibility protocol](e2ee-v2.md), and full v2.1 ciphertexts. The
values are regenerated by [`tools/gen-vectors.py`](tools/gen-vectors.py), and
the Rust test suite pins the same constants. The TypeScript suite pins the v2
AAD.

## Fixed inputs

| Input | Value |
| --- | --- |
| Suite | `x25519-aes-256-gcm-hkdf-sha256` |
| Service X25519 private seed | 32 × `0x03` |
| Service X25519 public key | `5dfedd3b6bd47f6fa28ee15d969d5bb0ea53774d488bdaf9df1c6e0124b3ef22` |
| Model | `demo-model` |
| Request nonce | `000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f` |
| Request timestamp | `1750000000` |
| Response id | `chatcmpl-123` |

These vectors cover AAD construction. Field encryption still requires a fresh
ephemeral key and AES-GCM nonce for every field.

## Request field AAD

For `messages.0.content`, the JCS bytes are exactly:

```text
{"algo":"x25519-aes-256-gcm-hkdf-sha256","field":"messages.0.content","model":"demo-model","nonce":"000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f","purpose":"aci.e2ee.request.v2","ts":1750000000}
```

## Response field AAD

For `choices.0.message.content`, the JCS bytes are exactly:

## Version 2.1

The v2.1 vectors fix every random input so the ciphertexts are reproducible.
Real clients and services draw a fresh request secret per request, and a fresh
ephemeral key and AES-GCM nonce per field.

| Input | Value |
| --- | --- |
| Suite | `x25519-aes-256-gcm-hkdf-sha256-v2.1` |
| Service key | the X25519 key above (seed 32 × `0x03`) |
| Client X25519 private seed | 32 × `0x04` |
| Client X25519 public key | `ac01b2209e86354fb853237b5de0f4fab13c7fcbf433a61c019369617fecf10b` |
| Request secret | 32 × `0x0a` |
| Request field ephemeral seed, AES-GCM nonce | 32 × `0x05`, 12 × `0x06` |
| Request-key ephemeral seed, AES-GCM nonce | 32 × `0x07`, 12 × `0x08` |
| Response field ephemeral seed, AES-GCM nonce | 32 × `0x09`, 12 × `0x0b` |

Model, nonce, timestamp, and response id are as above.

### Streamed response

A `"stream": true` request to the inputs above. The delta `Hello` is sealed to
the client key with ephemeral seed 32 × `0x0c` and AES-GCM nonce 12 × `0x0d`,
field `choices.0.delta.content`, response id `chatcmpl-123`. Each event carries
its MAC. The exact stream bytes, with `\n` line endings:

```text
data: {"choices":[{"delta":{"content":"97c3b10b4d6c133a78ea5dcc1cf6421d3f81ae37b1f628ce14ca6fce7730f3330d0d0d0d0d0d0d0d0d0d0d0df4e9f89190a3ecafd2eb8d3b91503afa4780983433"},"index":0}],"e2ee_mac":"902a797ccc56ecd1574b988d207f3866072f4752cd1d748968b085eb4426fb5b","id":"chatcmpl-123"}

data: {"choices":[{"delta":{},"finish_reason":"stop","index":0}],"e2ee_mac":"c512289034800b6ee774ffe28f76e1156c3b3ce78d7f549f46314f8cd390843e","id":"chatcmpl-123"}

data: [DONE]

```

A client accepts this stream and yields `Hello`, then a finish event with
`"finish_reason":"stop"`, then `[DONE]`, with no `e2ee_mac` members.

### Streams a client must reject

Each stream below differs from the one above in one way. A conforming client
fails it (§10.6).

| Change | Why it fails |
| --- | --- |
| In event 2, `"finish_reason":"stop"` becomes `"finish_reason":"length"`; the MAC is unchanged. | The MAC no longer matches the object. |
| Event 2's `id` becomes `chatcmpl-124`, with its own valid MAC `f7e12cef22bb7334f112385f17352dacfeca09cf5d3bac59d7cc06f18b13a328`. | Every event of a stream must carry the first event's `id`. |
| Event 1 has no `e2ee_mac` member. | Every response object must carry a MAC. |
| The stream starts with the line `id: 1`. | Only `data:` lines and comments are allowed. |
| The buffered response object from "Response MAC" above, served as `application/json`. | The request asked for a stream. |
